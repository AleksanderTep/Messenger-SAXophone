# Правила коммитов, push и Pull Request

Утверждены руководителем проекта scorpdestroy 27.10.2026 для дальнейшей работы.
Участники и переданные ими реквизиты: [docs/team.md](team.md).
Эти правила — соглашение команды; сами по себе они не включают защиту веток в GitHub.

## Ветки

| Ветка | Назначение | Как попадает код |
|---|---|---|
| main | Проверенная демонстрационная версия | PR из release/* после review и регресса |
| develop | Интеграция спринта | PR из ветки задачи |
| feature/S1-06-health | Новая функция | От актуальной develop |
| chore/S1-11-compose | Инфраструктура | От актуальной develop |
| docs/S1-10-git-workflow | Документы | От актуальной develop |
| test/S1-20-smoke | Проверки | От актуальной develop |
| fix/S1-xx-description | Исправление | От актуальной develop |
| release/0.1.0 | Подготовка релиза | От develop после интеграции всех зависимостей |

Bootstrap: develop создаётся на текущем origin/main без изменения истории main.
Уже опубликованная docs/S1-16-ui-mockups — отдельная задача с тремя исходными изображениями.
Прямой push в main/develop, force push и удаление чужих веток не допускаются.
При необходимости hotfix обсуждается отдельно, без обхода проверок.

## Коммит

Один коммит — одна понятная группа изменений одной зоны ответственности.
Формат: `S1-06: add service health endpoint`. Для связанной группы можно перечислить
несколько номеров, но не смешивать независимые backend/frontend/инфраструктурные изменения.

1. Проверить текущую ветку, status и актуальность основания.
2. Убедиться, что изменения соответствуют задаче, и выполнить относящиеся проверки.
3. Выполнить git add с явным списком файлов. Не добавлять весь рабочий каталог.
4. Просмотреть staged diff и список файлов; проверить отсутствие .env, ключей, токенов,
   node_modules, сборок, локальных журналов и персональных настроек.
5. Создать коммит с согласованными именем и email автора, переданными через параметры
   конкретного вызова Git. Не менять глобальную конфигурацию компьютера.
6. Проверить git show: автор, email, сообщение и файлы. Только затем push ветки.

Email должен быть связан с GitHub автора либо быть его точным GitHub noreply.
SSH-ключ подтверждает право push, а email связывает автора коммита с аккаунтом.
Использование имени другого участника требует явного указания руководителя и корректной
атрибуции реального вклада; распределение задач само по себе авторство не подтверждает.
Для реальной совместной работы можно добавить Co-authored-by. Даты всегда фактические.
Список владельцев задач не даёт права автоматически изображать их review или одобрение.

## Проверки перед push

| Изменение | Минимальная проверка |
|---|---|
| Документы/изображения | staged diff, читаемость, ссылки и состав файлов; тесты приложения не нужны |
| Backend | ruff, pytest; для схемы Alembic upgrade/check и тесты PostgreSQL |
| Frontend | lint, unit tests, build; при изменении экранов Playwright на 375 и 1440 px |
| Docker/proxy | compose config и up --build --wait, HTTP smoke |
| CI | Проверка YAML и соответствующих команд локально; после push проверить настоящий run |

Каркас вводится постепенно: ранний коммит может зависеть от следующей инфраструктурной
карточки. Такое ограничение явно описывается в draft PR. До готовности всей цепочки
его нельзя объявлять готовым к релизу. Полный CI включается отдельной карточкой S1-12.

## Pull Request

Заголовок содержит номер задачи. Описание объясняет проблему и результат, перечисляет
проверки с фактическим результатом, ограничения и зависимые PR. Используется шаблон репозитория.
PR задачи направляется в develop; main не используется как общая рабочая ветка.

Если серия зависима, следующая ветка начинается от предыдущей и открывает draft PR
с base предыдущей веткой. Это показывает только её собственные изменения.
После слияния основания base переводится в develop и проверки запускаются заново.
Независимые макеты и правила можно проверять отдельно от каркаса приложения.

Перед merge нужны реальное review хотя бы одного другого участника, закрытые замечания,
успешный существующий CI и выполненные критерии задачи. Нет workflow — нет подтверждённого CI;
для bootstrap-документов применяются проверки документов и человеческое review.
Рекомендуется merge commit для сохранения авторских коммитов серии. Squash не применять
ко всей серии разных авторов, если это потеряет корректную атрибуцию.

GitHub CLI/API требуют отдельной авторизации для создания PR; SSH-доступ для push
её не заменяет. Если авторизация PR отсутствует, ветка может быть опубликована,
а ссылка создания PR передаётся руководителю. Это не считается открытым PR.
Не включать auto-merge до появления реального review. Защиту main/develop
(reviews, запрет force push и required checks) владелец включает в настройках GitHub;
документ не утверждает, что она уже включена.

## Порядок поставки первого спринта

Правила/макеты → требования и структура → каркас API → схема и миграция БД →
общие UI-компоненты → React-оболочка → Docker/proxy → тесты → CI → итоговая сводка.
Точный перечень файлов задаёт commit-plan.json. Состав, проверки и зависимости
проверяются до публикации каждой группы; произвольная смена автора по кругу не допускается.

Плановая отправка может происходить раз в час, по одной группе. Пропущенные запуски
не догоняются массовыми push. Время создания и отправки остаётся настоящим.
Расписание — организация публикации уже подготовленного кода, а не свидетельство того,
что код писался в течение этих часов. При изменении файлов вне согласованного состава,
ошибке проверки или конфликте отправка останавливается до разбора причины.

## Pyrus и завершение спринта

Для задачи добавляется ссылка на PR/commit и результат проверок. Done только после
приёмки, review и merge, если этого требует критерий карточки. Обзор архитектуры,
командное review и подтверждение доступов нельзя заменить созданием документа.
S1-10: «Создать Git-репозиторий и правила ветвления», Pyrus #387881215.
После интеграции спринта создаётся release/0.1.0, проводится регресс, затем PR в main;
релизные исправления возвращаются в develop.
