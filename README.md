# Messenger SAXophone

Messenger SAXophone — учебный командный проект: веб-мессенджер, который разрабатывается командой из семи человек в течение четырёх недель.

Главная цель проекта — не только собрать рабочий MVP, но и отработать совместную разработку: постановку задач в Pyrus, работу с Git, Pull Request, Code Review, тестирование и выпуск общей версии приложения.

## MVP

В первую версию входят:

- регистрация и вход пользователя;
- поиск пользователей;
- личные диалоги один на один;
- отправка и получение сообщений без перезагрузки страницы;
- сохранение истории сообщений в PostgreSQL;
- веб-интерфейс для работы с диалогами.

Звонки, каналы, боты, передача файлов и сквозное шифрование не входят в первый MVP.

## Предварительный стек

- Backend: Python, FastAPI;
- Frontend: React, TypeScript;
- база данных: PostgreSQL;
- обновления в реальном времени: WebSocket;
- локальное окружение: Docker Compose;
- автоматические проверки: GitHub Actions;
- управление задачами: Pyrus.

Стек может уточняться в ходе проектирования. Существенные изменения фиксируются в задаче Pyrus и обсуждаются с командой до реализации.

## Роли в команде

У каждого участника есть основная зона ответственности, но роли не создают жёстких границ: участники могут помогать друг другу, проводить Code Review и брать задачи из соседних направлений.

1. Руководитель проекта / Tech Lead.
2. Backend-разработчик 1 — пользователи и авторизация.
3. Backend-разработчик 2 — чаты, сообщения и работа с БД.
4. Frontend-разработчик 1 — регистрация, вход и поиск пользователей.
5. Frontend-разработчик 2 — список чатов и окно переписки.
6. QA / разработчик автоматизации — тестирование и автоматические проверки.
7. DevOps / разработчик интеграции — Docker, CI и окружение.

## Работа с задачами

- Любое изменение должно быть связано с задачей в Pyrus.
- Номер задачи указывается в имени ветки, коммите и Pull Request.
- Перед началом работы исполнитель переводит задачу в `In Progress`.
- После открытия Pull Request задача переводится в `Code Review`.
- После проверки кода — в `Testing`.
- Статус `Done` ставится только после выполнения критериев готовности и слияния Pull Request.

## Git-процесс

### 1. Получить актуальную основную ветку

```bash
git switch main
git pull --ff-only origin main
```

Работу нельзя начинать от устаревшей локальной ветки `main`.

### 2. Создать отдельную ветку под задачу

```bash
git switch -c feature/TASK-014-registration
```

Допустимые префиксы:

- `feature/` — новая функциональность;
- `fix/` — исправление ошибки;
- `docs/` — документация;
- `test/` — тесты;
- `chore/` — инфраструктура и технические изменения.

Формат имени: `<тип>/TASK-номер-короткое-описание`.

### 3. Делать небольшие понятные коммиты

```bash
git add <изменённые-файлы>
git commit -m "TASK-014: add user registration"
```

Не добавляйте в Git файлы `.env`, пароли, API-ключи, токены и другие секреты.

### 4. Перед отправкой синхронизироваться с `main`

```bash
git fetch origin
git rebase origin/main
```

После разрешения конфликтов необходимо повторно запустить относящиеся к задаче проверки и тесты.

### 5. Отправить ветку и открыть Pull Request

```bash
git push -u origin feature/TASK-014-registration
```

В Pull Request укажите:

- ссылку или номер задачи Pyrus;
- что изменено;
- как проверить результат;
- известные ограничения, если они есть.

## Правила Pull Request

- Не отправлять изменения напрямую в `main`.
- Один Pull Request должен решать одну задачу.
- Автор самостоятельно просматривает изменения перед запросом ревью.
- Pull Request проверяет минимум один другой участник.
- Замечания Code Review исправляются в той же ветке.
- Слияние выполняется только после успешных тестов и одобрения.
- После слияния рабочая ветка удаляется.

## Если возникла проблема

Если задача заблокирована, исполнитель пишет причину в комментарии Pyrus, указывает, чья помощь требуется, и сообщает об этом команде. Не нужно молча ждать или менять согласованный API без обсуждения.
