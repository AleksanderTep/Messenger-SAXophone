# Стратегия проверки финального объёма

| Уровень | Где | Что доказывает |
|---|---|---|
| Unit/сервис | backend/tests/test_auth.py | Нормализация, hash, конфликты и базовые операции |
| API | TestClient в backend/tests | Коды 201/400/401/409, защита маршрутов, отсутствие hash в ответе |
| PostgreSQL | RUN_DB_TESTS=1, отдельная мигрированная БД | Реальные индексы, FK, миграции и ограничения |
| Frontend unit | frontend/src/App.test.tsx | Ошибки, загрузка, гостевой переход, сессия |
| Browser E2E | frontend/e2e/auth.spec.ts | register → login → profile → refresh → logout на 375/1440 px |
| Smoke | scripts/smoke.py и Compose healthcheck | Запуск процесса, БД и HTTP через proxy |
| Ручной разбор | Общая демонстрация | Участник сам показывает сценарий и объясняет свои файлы |

P0: не запускается приложение, невозможен вход/регистрация для валидных данных, доступ к чужому профилю, выдача password_hash/пароля, действующий токен после logout. P1: неверное сообщение об ошибке, отсутствие повтора сетевого запроса, неудобный мобильный layout при сохранённой основной функции.

Подтверждённые локальные результаты прежней проверки: 32 backend-теста PostgreSQL, 11 frontend unit-тестов и 5 browser E2E. Это сохранённые результаты, не новый запуск 28.10. Последний проверенный CI develop: https://github.com/scorpdestroy/Messenger-SAXophone/actions/runs/40540606835 .

При ошибке UI сохраняются screenshot и trace; workflow прикладывает их только при failure. При успешном запуске отсутствие failure-artifact нормально. Реальную передачу приложения на внешний production-сервер не тестировали.
